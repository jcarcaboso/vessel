Play monitor, events and workers: architecture overview

How events, the broker, worker modules, the account monitor and discrepancies fit together. This page is a visual summary of the implemented design; names and defaults match the code.

Details: messaging, events and workers reference (messaging-and-workers.md) · decisions: monitor plan · browser API: monitor API contract · operations: deploy/README.md

1. Summary

PostgreSQL is the record

Events, subscription progress, receipts, pending monitor requests, leases and discrepancies.

RabbitMQ is transport

It wakes subscribers and carries commands. A lost broker volume costs latency, not data.

Publish once

Publishers write an event in the business transaction and publish it once to a topic, knowing nothing about subscribers.

Subscribers recover

Each subscription owns its queue, filter, dead-letter queue, receipts, retries and catch-up from PostgreSQL.

Model: an Azure Service Bus–style topic with subscriptions on RabbitMQ through Wolverine. Publishers publish once and know nothing about who listens; each subscriber owns its queue, filters, dead-letter queue, receipts and recovery. PostgreSQL stays the record, so nothing depends on broker durability.

3. Projects and dependency direction

Domain and Application never reference Wolverine or RabbitMQ; architecture tests enforce it. All broker code lives in one adapter project, Vessel.Messaging, which feature modules plug into.

Module contract (IVesselModule)

  • Name — also the default deployment and envelope schema
  • Commands — point-to-point queues the module owns
  • Subscriptions — event subscriptions with filters it owns
  • AddRunningServices — handlers and hosted services, only in hosts that run it

Compiled-in registry, no plugin discovery. Today: monitor; tests and release checks add verification.

Unit of work

  • One top-level transaction per use case; nested calls participate and save, never commit
  • Commit ignores request cancellation; rollback keeps the original error
  • Events are staged before commit and published only after it
  • Image storage I/O refuses to run inside any transaction (incl. ambient/enlisted)

4. Events: one topic, many subscriptions

The Azure Service Bus model mapped onto RabbitMQ. Publishers write the event and its outbox envelope in the same transaction as the business change, then publish once. A subscription is a queue plus binding filters, declared by the module that owns it.

5. Delivery, receipts and catch-up

Live delivery and catch-up share one dispatcher. It locks the receipt row first, runs the handler's database effects inside a savepoint, and settles the receipt in the same transaction. The broker only wakes it up.

SituationReceiptBroker
Handler succeeds (or skips, or the event expired)delivered / skipped / expired, with effects, same transactionack
Handler or its save fails (retryable)effects rolled back to the savepoint; attempt counted; next attempt scheduledack (catch-up owns the retry)
Attempt cap, unsupported version or terminal handler errorfailed (visible; admin retry possible)dead-letter for diagnosis
Owner mismatch, unknown event id, or a queue this host does not runno effects, no receiptdead-letter, logged by IDs only
Event pruned (identity in event_dedup) or retained below the floorknown history, not re-deliveredack
Already settled, not responsible, or not yet dueunchangedack
Database unavailable mid-deliverywhatever committedack — catch-up finds the event later

Retention (hourly)

Deletes only a contiguous prefix of events older than RetentionDays (90), stopping before the lowest pending receipt. Age decides: a subscription behind the window is marked lagging with a visible gap instead of holding history. Dedup and fill identities survive pruning.

Accepted limit

If a whole transaction fails at commit time (after a successful handler), the attempt is recorded in a follow-up transaction. The cap bounds recorded attempts, not every rolled-back run. Safe because handlers touch only the database and are idempotent.

6. Notification Hub (designed, not built)

The hub is one subscription. It owns your notification rules and hands each message to per-provider queues. Adding Discord later means adding a provider, never touching publishers or the event contract.

Provider queues are transport too: providers recover unsent work from the hub's delivery records using stable delivery IDs. External sends are at-least-once, so providers must tolerate duplicates.

7. Worker modules and independent scaling

One image, many deployments. Each worker runs the modules in Vessel:Worker:Modules; each logical deployment has its own Wolverine envelope schema, recorded in messaging_deployments so a schema cannot be reused by a different module set.

Scheduler

Every 30 s: discover eligible accounts (paged, set-based), claim due rows with FOR UPDATE SKIP LOCKED and a renewable 5-minute lease. At most two account reads run at once per owner, across all workers and API refreshes.

Commands

MonitorAccountCommand → vessel.commands.monitor. The listener only validates against monitor_accounts and wakes the scheduler; it never reads a venue.

Health

Heartbeat row + file advance only after a successful discover/claim pass; the healthcheck reads the configured timeout. Failures log exception type and IDs only.

8. Monitor run lifecycle

Venue reads happen outside database locks. Results are applied only by the current lease holder, under the account lock, and only if the observation is newer than what is stored.

Watches on leftover orders

Linked stops, targets and entries of Closed/Cancelled Plays stay watched. A fresh filled/cancelled status ends a watch on any read; absence needs a complete current book (historical "open" rows don't count). After 7 days (WatchLifetime) a watch ends as a visible unverifiable, never "gone".

Coverage stays honest

Adapters report OmittedExecutions (Lighter fills without P&L or with unverified fees; Hyperliquid/RISEx fills on unknown markets). Any omission makes the run degraded and fill-based checks unknown. Price touches are never fills.

9. Discrepancy state machine

One pure function (DiscrepancyLifecycle) maps (record, input) → (new record, event). Inputs: fresh present, fresh absent, incomplete, expiry tick, dismiss. A durable PublishedTransition guarantees that everything announced stays visible and every announcement gets exactly one close.

Stop protection

Only real stop mechanics count (shared OrderMechanics). Targets never protect; wrong-side stops protect nothing; unknown order types → unknown. Manual linking refuses a take-profit on a stop level.

Several Plays on one instrument

A whole-position stop covers siblings only on the same contract with a compatible closing side. Opposite Plays that net out are unknown per Play — never "protected" by net equality.

Kinds

protection.missing · .short · .excess · .cancelled · .orphaned · entry.orphaned · position.excess · .short · .missing · .opposite · fill.unlinked · level.drift

10. Browser live updates

All cursor syntax lives in one frontend module (event-cursor.ts). The browser stream is not a durable subscriber; the database is.

11. Operations

Offline commands (API binary)

  • provision-messaging — declare topology, register subscriptions (insert-only), record deployments
  • rotate-event-epoch — mandatory after a database restore
  • retry-event-receipts — bounded admin retry of failed receipts
  • deregister-event-subscription — release a removed subscription

The API and worker never migrate or declare topology at startup.

Procedures

  • Upgrade / backup: stop web api worker, then migrate (EF bundle → provisioning)
  • Restore: stop all → restore PostgreSQL → rotate-event-epoch → provision → start
  • Broker volume lost: provision again; subscriptions catch up from PostgreSQL
  • RabbitMQ users: admin for migrate; optional least-privilege app user for API/worker

13. How it is tested

Tests use only disposable PostgreSQL and RabbitMQ (Vessel_TEST_POSTGRES, Vessel_TEST_EVENT_RABBIT) and synthetic data. The complete map is in the reference.

14. Not built yet

Separate plans

  • Notification Hub: subscription notifications, providers Telegram first, then Discord and in-app
  • Price and drawing alerts (near-real-time path)
  • Venue user streams as a capability, incremental fill cursors
  • A normalized liquidation fact for a position.liquidated event

Known gaps

  • Subscription lag, gaps and failed receipts are visible in PostgreSQL only, not yet in an API or health check
  • Settings fencing is coarse: a portfolio move also supersedes an in-flight run
