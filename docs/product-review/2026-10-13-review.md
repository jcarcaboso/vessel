# Vessel review after the October 13 update

Reviewed `7559248f838068faff8cf8146844a031bc2a67c9`, after a fast-forward pull from `a51c7f2`. The pull brought in 129 commits through the v0.1.0 packaging merge. Previous review files were preserved. This review proposes work; it does not authorize implementation or establish that release images have been published.

## Recommendation

**Fix execution integrity and save-time data loss before adding more analytics or trading tools.** Vessel can now save plans, track linked executions and report outcomes. The original "nothing can be saved or measured" diagnosis is obsolete.

The next useful feature is a way to finish the trading journal for **manual trades and imported history**, followed by a complete position-risk summary and a short structured review. More chart indicators would be lower value.

This is a product-quality assessment, not a claim that using these features will improve investment returns.

## Six confirmed defects

P1 means incorrect executed exposure or final status that can also contaminate sizing feedback. P2 means a material editing, correction or data-loss defect. None of these findings indicates that Vessel sends orders to an exchange.

| ID | Priority | Reproduction and consequence | Smallest useful correction |
| --- | --- | --- | --- |
| R1 | P1 | An entry order says 2 units filled, but only 1 entry fill is retained. A 1-unit exit closes the Play. The missing fill arrives later and the record is still Closed with 1 unit open. Sizing counts a win; Review rejects the incomplete result. | Require known order/fill completeness before final closure and before scoring a sizing outcome. Keep incomplete exposure explicit. |
| R2 | P1 | A target-price sell from an earlier position executes before this Play's buy. Both orders match the new Play and close it. Review rejects the chronology, but sizing counts the result. | Validate chronological exposure for planned targets and stops as well as unplanned exits. An exit order may be placed early; an exit fill cannot close an entry that has not happened. |
| R3 | P1 | A buy/open fill can be manually linked as the exit of a long Play. Two buys become "entered 1, exited 1, open 0", although they represent long 2. Automatic entry matching can also mistake closing an old short for opening a new long. | Validate normalized side and position effect at matching, owner linking and lifecycle transition. Owner confirmation resolves attribution, not the meaning of a fill. |
| R4 | P2 | The API lets a Closed Play's exit link be deleted. The Play remains Closed with open quantity 1. Restoring the link returns 409 because Closed Plays cannot link orders. The normal Closed UI hides unlink, but the API and stale requests remain exposed. | Reject terminal unlinking under the existing account lock. Do not invent reopening merely to fix this missing guard. |
| R5 | P2 | A filled long Play accepts a revision to Short. Later real sell exits stop matching because the matcher uses the revised direction. Filled-entry price/share guards do not protect direction. | Lock direction after an entry fill, on the server and in the editor. Preserve permitted stop/target revisions. |
| R6 | P2 | Editing an image note while Save is pending loses the new note when the response arrives, and the button reads Saved. | Merge only server identity and saved metadata into the current evidence object; preserve current note/markup and keep the editor dirty. |

### R6 browser reproduction

1. Open a new Play on the isolated API, choose the public Hyperliquid BTC catalogue, and capture the chart.
2. Write a note, then Save. Hold the successful create response for 10 seconds to simulate a slow connection, within the client's 15-second timeout.
3. While the button says Saving, replace the note with `New annotation DURING 10-second save`. The field remains enabled.
4. Release the response. The upload and save complete.
5. The previous note reappears and the button says Saved.

The browser used the real create/upload APIs. Only response delivery timing was delayed; no successful server response was fabricated. The fetch override was removed afterward. A first longer delay exceeded the client's timeout and was discarded as inconclusive; it is not the evidence for this finding.

The destructive reconciliation is the map at `PlaysPage.tsx:118`. It substitutes the entire previously sent evidence object instead of copying its `serverId` and `savedState` onto the current object.

Acceptance test: use a deferred create/update or upload response, edit a note before it resolves, then assert that the new note remains, the server identity is recorded and Save stays enabled. Also test markup edits and removal during save. The note is browser-confirmed; markup has the same replacement path but was not separately reproduced.

## Required next work

### 1. A trustworthy execution record

Resolve R1–R5 together before relying on the sizing feedback. Review already has useful completeness and chronology guards. Apply equivalent invariants at the point where execution links affect status and sizing, rather than allowing a bad Closed record and excluding it later.

Show why a record cannot be reconciled. "Closed", "one unit open" and "excluded from Review" should not coexist without a correction path. Add a drill-down listing the exact excluded Plays and the missing or contradictory facts; the present coverage section reports counts, not a repair queue.

Acceptance example: entry order 2, retained entry fills 1, exits 1 means **incomplete history**, not a confirmed full close. Later ingestion of the second entry keeps remaining quantity visible.

### 2. Manual executions and retrospective review

A manual account can save and plan a Play, but cannot record a manual fill or complete Open → Closed through the current UI. The browser confirmed an Execution tab saying manual instruments are not tracked, with only pause/cancel available for the planned record.

Add explicit manually entered executions with timestamps, quantity, price, fees and source. Do not make a "mark profitable" shortcut or pretend a price touch filled an order.

Separately, let the owner select retained activity and create a **retrospective** review record. Preserve missing openings, ambiguous concurrent Plays and unknown initial risk. Do not supply a pre-trade thesis or R denominator after the fact.

Acceptance example: a manual long entered at 100 and exited at 95 can be closed with explicit user-supplied execution facts. An imported completed operation can receive a lesson without claiming that its lesson was a pre-trade plan.

### 3. Complete the whole-position money summary

Do not replace the arithmetic already built. Extend it to show:

- All-stops planned loss and all-targets planned gain.
- Aggregate R:R with explicit partial-target and missing-stop coverage.
- Risk as a share of a clearly named account value or manual reference, not a mixed wallet/equity sum.
- Optional fee and slippage assumptions, plus a separate funding estimate when the holding-period assumption is known.
- All-entry versus entry-alone risk paths, using the existing liquidation warnings without claiming broker accuracy.

Hypothetical linear-contract example: 0.1 units entered at 100 with stop 95 risks 0.5 quote units; 0.1 entered at 90 with stop 85 risks another 0.5. The summary should show total planned loss 1 before costs. If the second stop is absent, show known risk 0.5 plus one unprotected/unknown tranche, not total risk 0.5.

The current summary has only margin, position size, quantity and average entry. Per-exit loss/profit and per-entry R:R exist elsewhere. Adding an unpriced second entry currently leaves a priced-only average and derived quantity visible. Label these provisional rather than implying a complete plan.

### 4. Funding and history coverage

Imported fills are already retained. The earlier recommendation to "start storing history" is stale. The remaining work is durable scheduled ingestion, bounded backfill, missed-period detection, import/export recovery and a visible coverage ledger.

Keep execution fees, separate funding cashflows and adjustments distinguishable. Do not allocate account/instrument funding to simultaneous Plays arbitrarily.

Hypothetical example: gross execution result +120, execution fees 35 and separately recorded funding cost 110 produce −25. A chart of execution-only results must not be labelled funding-complete performance.

The official Hyperliquid API documentation distinguishes `userFills`, capped at the most recent 2,000 fills, from `userFillsByTime`, at most 2,000 per response within the latest 10,000. Those limits do not prove that Vessel has captured a continuous history. The current adapter's bounded read and lack of a backfill cursor remain visible in source. See the precise references in the [product delta](2026-10-13-product-delta.md#current-external-verification).

### 5. A short structured review

Extend the existing free-text Review and Needs review queue. Keep the first version to optional adherence, one mistake tag, a lesson and an action for next time. Preserve text and revision provenance.

Example: "Won +2R, but doubled size after invalidation" should remain a profitable outcome and a process violation. "Lost −1R, followed the plan" should not be scored as a bad decision.

Only then add setup/adherence comparisons with sample counts. Avoid a generic plan-quality score and avoid presenting small samples as an edge.

### 6. Protection and portfolio risk

Two distinct questions remain unanswered:

- **Protection:** does a compatible live stop cover the current quantity, and when was that checked? A planned line is not a working stop.
- **Portfolio heat:** what is the known stop risk across concurrent Plays, and which exposures have unknown risk?

Example: position 1 BTC with linked stop size 0.6 BTC should show 0.4 uncovered, not a green protected state. Three 150-unit risks on a 10,000-unit reference total 4.5% before costs, but the display must still identify unmatched venue exposure and unknown stops.

Start with deterministic totals and unknown counts. Leave correlation models and beta weighting for later. A server-side monitor should report stale or stopped coverage; the current viewed-Play checks and chart SSE do not constitute durable monitoring.

## UI and UX changes worth making

1. **Keep the locked layout.** The updated chart begins around y=394 without a warning at 1280 px; the tested 1440 px venue view with a liquidation notice begins around y=467. The old y≈659 claim is not a current measurement. These are different states, not a timed usability comparison.
2. **Compress mobile context without reordering sections.** The saved manual Play's chart starts at y≈871 at 390 px, after account/context/actions. Compact context disclosure and a visible save-state/action affordance would reduce scrolling. The selected entry still has to compete with the chart and journal above it in the approved stack.
3. **Put risk and result together.** Use the existing Summary location for whole-position loss/gain/R:R. Keep the selected-entry detail available.
4. **Make exclusions actionable.** Review correctly rejected the bad fixtures, but "2 excluded" does not identify what to fix. Link to the affected Plays and execution reason.
5. **Add search to the Plays list.** Current filters are In progress, Closed and cancelled, and All. Title/instrument/account search and sorting matter before hundreds of records accumulate. Do not build a separate dashboard.
6. **Make partial plans visibly partial.** A 100% quantity allocation does not imply that all prices/stops are present. Separate allocation completeness from priced/risk-covered completeness.
7. **Clarify limitations at their controls.** Manual Play execution needs a concrete unsupported-state explanation. Planning-cost exclusions and liquidation assumptions should not rely solely on hover titles.
8. **Correct the cross-margin tooltip.** `PositionEditor.tsx` says "Cross margin liquidates further away." Cross liquidation depends on shared collateral and other positions; it is not an unconditional guarantee. Use "Cross liquidation depends on account-wide collateral and exposure; check the venue." The [product delta](2026-10-13-product-delta.md) includes official support.
9. **Guide first-use toward an account, not mandatory grouping.** The empty Overview asks users to create a portfolio first, although null/unassigned membership is fully supported. Offer Add account first and optional portfolio assignment.

- Wrong-side stops produce an inline explanation and block Save.
- BTC catalogue leverage typed as 100 normalized to the loaded maximum of 40 on blur; the presets reflected the maximum.
- A stop beyond estimated liquidation produces a prominent warning.
- Adding a second entry splits the quantity shares 50/50. The old blank-share/green-allocation example does not reproduce on that path.
- The expanded entry editor fit at 320 px, used unique IDs and restored focus to its trigger after Escape.
- Review and Plays had no page-level horizontal overflow at the tested 390 px width; the expanded editor had none at 320 px.
- Overview no longer says Plays is unavailable. Review has explicit metric definitions, small-sample labels and coverage.
- The chart attribution now carries the title "Charting by TradingView", which supplies an accessible name. The old blanket unnamed-link finding should not be repeated.

Dense overlapping chart tags, every venue failure state, touch dragging and screen-reader behavior were not exhaustively re-audited. The old B4 screenshot is not evidence of a current defect.

## Suggested build order

1. **Integrity patch:** R1–R6, shared execution eligibility checks for status/sizing, regression tests and explicit incomplete-execution states.
2. **Complete the journal:** manual execution lifecycle, retrospective attribution and review origin. Do not merge venue operations and Plays into one concept.
3. **Make planning readable:** whole-position money summary, partial-plan coverage, source-labelled costs and mobile density improvements within the locked layout.
4. **Protect data and exposure:** ingestion coverage/backfill, separate funding, protection quantities, known/unknown portfolio heat and durable monitoring.
5. **Make review useful:** structured lessons/adherence and small-sample-aware comparisons. Versioned strategies follow the owner's plan.

The first slice is a recommendation to fix defects, not permission to start coding in this review branch.
