Vessel 0.2.0 adds a background Play monitor. A separate worker now watches your
venues, links orders, moves Plays through their lifecycle and flags what doesn't
match your plan, without a browser open. It adds two services, a message broker
and five database migrations, so read the upgrade steps first.

## Highlights

### A monitor that works while you are away

- A new `worker` service (the same API image) checks every account that has an
  active Play, or a closed Play whose orders may still rest, every 10 minutes by
  default. It imports fills and orders, links what matches, and moves Plays to
  Open or Closed on its own.
- **Check** on an account or in a Play's Execution tab asks for an extra run now.
  The answer is immediate and the result arrives on its own. A short cooldown
  keeps repeated presses from reading the venue again.
- Opening a Play or leaving a page open never reads a venue. Account **Refresh**
  works as before.
- A price touch is never treated as a fill, and an unknown value stays unknown.

### Discrepancies

- Vessel flags, and never corrects: a missing, cancelled, short or excess stop;
  stops, targets and entries still resting after a Play ended; planned levels
  that drifted; venue positions that disagree with your open Plays; and fills
  not linked to any Play.
- A real stop is recognised by how the order behaves, not by its label. A
  take-profit never counts as protection, and Plays that cancel each other out
  on one instrument show "unknown", not "protected".
- Each one can be dismissed with a note. If a subject can't be observed for 7
  days, the record shows **unverifiable**: it is neither resolved nor still
  checked.
- Accounts show a badge when the monitor is degraded, stale or has lost its
  worker, and say why. Coverage gaps (omitted fills, truncated history) make the
  affected checks unknown instead of guessing.

### Live updates

- Changes appear in the browser without a reload. The page reads the current
  position first, then follows an authenticated event stream, and backs off when
  the connection drops. After a database restore, open pages reload by
  themselves.

### A cleaner foundation

- Every database write now goes through one unit of work, and every Play,
  execution, link, discrepancy and monitor change is recorded as an event in the
  same transaction. Events are published once to a RabbitMQ topic; each
  subscriber keeps its own queue and catches up from PostgreSQL if the broker
  loses anything. This is the base for notifications, which are not part of this
  release.

## Upgrading from 0.1.3

This release adds two services, `rabbitmq` and `worker`, and five migrations
(`VesselEvents`, `AccountMonitor`, `MessagingDeployments`, `PlayDiscrepancies`,
`PlayDiscrepancyUnverifiable`). The `migrate` service now also provisions the
broker.

1. Back up the database, evidence and credential key ring.
2. Add `RABBITMQ_USER` and `RABBITMQ_PASSWORD` to `.env` (URL-safe values) and
   keep `Vessel__Auth__OwnerId` set. The broker's AMQP port is never published
   and its management page binds to loopback.
3. Set `VESSEL_VERSION=0.2.0` and follow the
   [upgrade procedure](https://github.com/jcarcaboso/vessel/blob/v0.2.0/deploy/README.md#from-v013-to-v020-the-account-monitor).
   Stop web, API and worker while `migrate` runs.
4. After a database restore, always run `rotate-event-epoch` before starting any
   host, so open browsers reload. The restore procedure now includes it.
5. To go back, restore the backup rather than starting an older image.

Installations upgrading from older versions apply the earlier migrations in the
same run.

## Images

Linux amd64, in [`skorcius/vessel`](https://hub.docker.com/r/skorcius/vessel):

- `skorcius/vessel:api-0.2.0`
- `skorcius/vessel:web-0.2.0`

`api-latest` and `web-latest` point to these images. The `worker` service uses
the API image. Deploy the fixed versions for predictable upgrades.

## Known limits

- Checks are periodic (every 10 minutes by default), not real time.
- There is no notification channel yet. Events reach the browser and are
  recorded for a later Notification Hub.
- Subscription lag, gaps and failed deliveries are not shown in the app. The
  [operations reference](https://github.com/jcarcaboso/vessel/blob/v0.2.0/docs/architecture/messaging-and-workers.md)
  has SQL to inspect them and commands to retry failed receipts.
- A worker running only other modules has no heartbeat of its own; only the
  monitor module writes one.
- Lighter Standard accounts exclude fee-bearing or unverified-fee fills, which
  leaves the checks that depend on them unknown.
- Activity still works out every operation from all retained fills on each
  request, then returns one page.
