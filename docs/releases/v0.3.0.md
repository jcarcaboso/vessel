Vessel 0.3.0 adds opt-in wallet sign-in with separate journals, an in-app
Notification Hub and settled venue funding. Token sign-in remains the default.

**Read before upgrading:** the order-identity migration has no backfill. It
refuses a database containing imported orders, fills or Play order links.
There is no retained-data upgrade path for those installations. Preserve a
verified backup and the old installation before deliberately creating a fresh
database and evidence store. Do not bypass the guard or clear individual tables.

## Highlights

### Wallet sign-in and separate journals

- Sign in with an Ethereum externally owned account through an injected wallet.
  Each user has a separate journal. A signature proves sign-in, never approves
  a transaction or grants trading permission.
- Manage your profile, linked wallets and sessions. Linking or removing a
  wallet requires a fresh action-bound signature. Sign-out and operator
  revocation invalidate server sessions and already-open streams.
- Operators manage invitations, wallets and access through explicit offline
  commands. Operator status does not grant application access to other journals.
- Background monitoring, event delivery and notifications keep owner-scoped
  progress. Venue read capacity is coordinated across owners through PostgreSQL.

Wallet mode is optional and requires HTTPS outside Development. Real-wallet
acceptance, including an EOA connected to a non-mainnet network, is still
owner-pending. Keep registration `Closed` until that check is recorded.
Synthetic Chromium and Firefox checks do not replace it.

### In-app notifications

The Notifications page, unread badge and timed popups report retained Vessel
events. Preferences control in-app delivery; a separate notifications worker
catches up from PostgreSQL. Popup claims prevent duplicate display across tabs
and reloads. External channels and browser system notifications are not included.

### Settled funding and safer order identity

- Refresh imports a bounded 30-day window of actual settled funding from
  Hyperliquid, RISEx, Lighter and Lighter on Robinhood Chain. Activity separates
  attributable payments from unassigned ones and preserves exact signed amounts
  and coverage limits.
- Funding stays separate from execution net when its inclusion in venue PnL
  cannot be proven. Review, sizing and Play attribution are unchanged.
- Orders are identified by account, instrument and venue order ID. Play links
  use Vessel's internal order ID, so reuse of a venue ID on another instrument
  cannot attribute that instrument's fills to the wrong Play.

Account pickers and allocation legends show account identity. The connection
screen loads without the whole workspace, and health reports the monitor and
notifications workers separately. The adversarial review also fixed monitor
starvation, stalled session-stream revalidation and cross-tab identity races.

## Installing or moving from 0.2.0

Release publication does not upgrade an installation or apply migrations.

1. Stop every API, web and worker instance on every host, including
   `worker-notifications`. Back up the database, evidence and credential key ring
   and verify that the old installation can be restored.
2. If imported orders, fills or Play order links exist, **do not run an in-place
   upgrade**. The migration refuses them. A deliberate fresh database/evidence
   installation is required; existing history is not automatically transferred.
3. Set `VESSEL_VERSION=0.3.0` and use both matching images. Preserve all selected
   storage, credential and TLS overlays. Keep Token mode unless explicitly
   opting into Wallet mode. Add `worker-notifications` to custom Compose image
   overrides and stop/backup procedures.
4. Follow the
   [v0.3.0 upgrade runbook](https://github.com/jcarcaboso/vessel/blob/v0.3.0/deploy/README.md#from-v020-to-v030).
   The explicit `migrate` service validates configuration without a database
   connection, then applies the identity bundle, journal bundle, owner bootstrap
   and messaging provisioning. The database role needs database `CREATE`
   privilege. No host migrates at startup.
5. For Wallet opt-in, configure the allowed HTTPS origin and the existing owner
   GUID, clear the bearer token, retain the Wallet overlay and bind only the
   operator's public wallet address through the offline command. Never supply
   a private key or seed phrase. Registration stays `Closed` until acceptance.
6. After any restore, follow the
   [identity recovery procedure](https://github.com/jcarcaboso/vessel/blob/v0.3.0/deploy/README.md)
   before starting hosts. In Wallet mode, review restored identities and run
   `identity reset-after-restore`; revocation alone does not reconcile restored
   wallets, roles or invitations. Rotate the event epoch and provision messaging.
   Rollback requires matching old images and the pre-upgrade backup, not down
   migrations.

## Known limits

- WalletConnect, smart-contract wallets, user/journal deletion and password/email
  recovery are not supported. `Open` and `AllowList` registration remain
  unsupported until per-user account/evidence quotas exist.
- Monitor checks remain periodic, not real time. A price touch is never a fill.
  Limits on user API requests are per process, not a global cap on all venue
  reads.
- Missing or unverified venue fees/PnL still limit imported execution coverage.
  Funding is not added to execution results without a proven basis.
- Host and database administrators control the underlying installation. Operator
  journal isolation is an application boundary, not protection from the host.
